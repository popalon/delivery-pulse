# Roadmap DeliveryPulse

Каждый этап завершается отдельным проверяемым результатом. Следующий этап не
должен скрывать незавершённые критерии предыдущего.

## Этап 0. Проектирование

Результат: согласованный аналитический контракт до написания генератора.

Критерии готовности:

- [x] описаны бизнес-задача, границы и пользователи;
- [x] предложена структура проекта;
- [x] определены таблицы, поля, ключи и ограничения;
- [x] определены основные метрики, зерно и правила выборки;
- [x] сформулировано не менее восьми проверяемых гипотез;
- [x] выделены 4–6 гипотез для обязательной глубокой проверки;
- [x] зафиксированы RUB, `Europe/Moscow`, матрица статусов и правила `NULL`;
- [x] зафиксированы правила кроссплатформенности и работы Codex;
- [x] настроен `.gitignore` для локальных и генерируемых артефактов.

## Этап 1. Каркас Python-проекта

Результат: устанавливаемый локальный пакет и минимальный набор инструментов.

Критерии готовности:

- [ ] создан `pyproject.toml` с зафиксированными диапазонами зависимостей;
- [ ] создан пакет `src/delivery_pulse`;
- [ ] единая конфигурация путей реализована через `pathlib.Path`;
- [ ] команды установки описаны отдельно для Linux и Windows;
- [ ] настроены `pytest`, форматирование и статические проверки;
- [ ] базовые проверки запускаются без PostgreSQL, Docker и Bash-зависимости.

## Этап 2. Генерация синтетических данных

Результат: воспроизводимые связанные исходные таблицы.

Критерии готовности:

- [ ] генератор принимает seed, период и объём;
- [ ] одинаковые параметры дают одинаковые данные;
- [ ] данные соответствуют модели и не содержат реальных сущностей;
- [ ] бизнес-зависимости и аномалии документированы;
- [ ] не все гипотезы подтверждаются; предусмотрены исчезающие после контроля и
  сегментные эффекты;
- [ ] созданы стартовые пробеги и предпериодное обслуживание автомобилей;
- [ ] операционные перегрузы отделены от искусственных дефектов;
- [ ] технический quality issue manifest воспроизводим и доступен только тестам;
- [ ] есть малый профиль для тестов и основной профиль для анализа;
- [ ] данные записываются в `data/raw/` и не попадают в Git;
- [ ] тесты проверяют детерминированность и ссылочную целостность.

## Этап 3. Контроль качества данных

Результат: автоматический отчёт о пригодности данных к анализу.

Критерии готовности:

- [ ] проверяются схема, ключи, пропуски, диапазоны и категории;
- [ ] проверяются временные и межтабличные бизнес-правила;
- [ ] критические ошибки отделены от предупреждений;
- [ ] контролируемые дефекты обнаруживаются тестами;
- [ ] manifest не используется аналитическим кодом и не попадает в витрины;
- [ ] проверяется матрица статусов и семантика финансовых `NULL`/`0`;
- [ ] ноутбук качества объясняет влияние дефектов на метрики;
- [ ] правила исправления не уничтожают исходные данные.

## Этап 4. DuckDB и SQL-слой

Результат: локальная аналитическая база и воспроизводимые витрины.

Критерии готовности:

- [ ] DDL согласован с `docs/data_model.md`;
- [ ] загрузка таблиц выполняется из Python кроссплатформенно;
- [ ] SQL-файлы не содержат машинно-зависимых путей;
- [ ] реализованы все обязательные витрины;
- [ ] для каждой витрины проверены зерно и уникальность ключа;
- [ ] SQL-метрики сверены с эталонными Python-расчётами;
- [ ] файл базы хранится локально и исключён из Git.

## Этап 5. Исследовательский анализ и визуализация

Результат: воспроизводимый EDA с объяснением структуры потерь.

Критерии готовности:

- [ ] описаны объём, период и качество анализируемой выборки;
- [ ] изучены SLA, опоздания, прибыльность и компоненты затрат;
- [ ] надёжность автомобилей нормализована на километры и часы рейсов;
- [ ] выполнены срезы по маршрутам, клиентам, времени и ресурсам;
- [ ] графики читаемы и воспроизводимы;
- [ ] выводы отделены от наблюдений и ограничений;
- [ ] тяжёлая логика вынесена из ноутбука в `src` или `sql`.

## Этап 6. Проверка гипотез

Результат: таблица решений по гипотезам с оценкой эффекта.

Критерии готовности:

- [ ] для 4–6 приоритетных гипотез определены выборка, метрика, контроль факторов
  и метод глубокой проверки;
- [ ] остальные гипотезы явно помечены как дополнительные;
- [ ] проверены предпосылки выбранных статистических методов;
- [ ] учтены множественные проверки, где необходимо;
- [ ] приведены размер эффекта и интервал неопределённости;
- [ ] корреляционные выводы не названы причинными;
- [ ] результаты воспроизводятся кодом.

## Этап 7. Бизнес-рекомендации

Результат: приоритизированный план действий.

Критерии готовности:

- [ ] выявлены главные зоны задержек и убытков;
- [ ] рекомендации связаны с измеренным эффектом;
- [ ] для рекомендаций указаны владелец, сложность, риск и KPI;
- [ ] предложены пилоты или эксперименты для причинной проверки;
- [ ] описаны ограничения синтетических данных;
- [ ] README содержит итоговые результаты и навигацию.

## Этап 8. Усиление инженерного контура

Только после отдельного согласования: PostgreSQL, Metabase, Docker Compose и
GitHub Actions.

Критерии готовности будут определены перед началом этапа; эти технологии не
должны становиться обязательными для локального базового сценария.
