# AGENTS.md

Правила распространяются на весь репозиторий DeliveryPulse.

## Контекст

DeliveryPulse — портфолио-проект аналитики данных вымышленной логистической
компании. Главная задача — объяснить опоздания и убыточность перевозок и
предложить проверяемые бизнес-изменения.

## Обязательные правила

1. Не использовать реальные данные компаний или персональные данные.
2. Не добавлять секреты, токены, пароли и локальные файлы окружения.
3. Не коммитить `.venv`, базы данных, сгенерированные датасеты, кэш и выводы
   ноутбуков большого размера.
4. Не использовать абсолютные пути и пути, зависящие от имени пользователя.
5. Все пути в Python строить через `pathlib.Path` относительно корня проекта
   или явно переданного каталога.
6. Основной сценарий не должен зависеть от Bash. Для запуска документировать
   отдельные команды Linux и Windows.
7. Код и SQL должны одинаково работать на Linux и Windows.
8. Случайность должна управляться явным seed; не использовать неявное глобальное
   случайное состояние.
9. Не добавлять PostgreSQL, Metabase, Docker Compose или GitHub Actions без
   отдельного запроса пользователя.
10. Не начинать следующий крупный этап без сверки с `ROADMAP.md`.

## Источники истины

- бизнес-требования и границы: `PROJECT.md`;
- этапы и критерии готовности: `ROADMAP.md`;
- таблицы и связи: `docs/data_model.md`;
- формулы метрик: `docs/metrics.md`;
- аналитические гипотезы: `docs/hypotheses.md`.

При расхождении сначала обновить документацию и тесты, затем реализацию.

## Правила реализации

- Python 3.11+, код пакета — в `src/delivery_pulse`;
- функции с бизнес-логикой должны иметь type hints и краткие docstrings;
- денежные расчёты в хранилище — `DECIMAL`, не бинарный `FLOAT`;
- время хранить в UTC; локальную временную зону моделировать явно;
- SQL использовать для витрин и проверяемых агрегаций, Python — для генерации,
  статистики, оркестрации и визуализации;
- переиспользуемую логику выносить из ноутбуков в `src` или `sql`;
- ноутбуки выполнять в порядке числовых префиксов;
- не изменять raw-данные на месте;
- все категориальные значения и имена полей — `snake_case`;
- изменение определения метрики сопровождается обновлением документации и
  теста на фиксированном примере.

## Проверка изменений

Перед завершением задачи:

1. запустить узкие тесты изменённого компонента;
2. при возможности запустить весь `pytest`;
3. проверить, что генерируемые файлы не попали в Git;
4. проверить отсутствие абсолютных путей и секретов;
5. сообщить, какие проверки выполнены и какие не удалось выполнить.

Тесты должны покрывать ключи, ссылки, бизнес-ограничения, детерминированность,
формулы метрик и зерно витрин.

## Работа с Git

- сохранять пользовательские изменения;
- не выполнять destructive-команды без прямого разрешения;
- делать небольшие тематические изменения;
- не коммитить и не публиковать изменения без явной просьбы;
- не переписывать историю;
- перед предложением коммита проверить `git diff` и `git status`.

## Документирование

README должен давать краткий путь запуска отдельно для Linux и Windows.
Существенные аналитические решения должны описывать допущения, выборку,
ограничения и возможность воспроизведения. Нельзя представлять корреляцию как
доказанную причинность.
